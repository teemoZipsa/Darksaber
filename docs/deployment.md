# Production Deployment

This project is deployed as a production network game. The deployment path is:

- Vercel: static Vite client
- Render Web Service: Node auth/world WebSocket server
- Neon Postgres: managed account/session/character/save database

Docker is not the deployment path for this project. PostgreSQL is operated as a
managed production database through `DATABASE_URL` so account data can be backed
up, restored, and kept outside any local machine.

## Architecture

```text
Browser
  -> Vercel static client
  -> HTTPS auth API on Render
  -> WSS world WebSocket on Render
  -> Neon managed PostgreSQL
```

The client must be built with both production server URLs:

```text
VITE_AUTH_SERVER_URL=https://<render-service-host>
VITE_WORLD_SERVER_URL=wss://<render-service-host>
```

The server must run with:

```text
NODE_ENV=production
DATABASE_URL=<Neon pooled connection string>
AUTH_JWT_SECRET=<long random secret>
AUTH_ALLOWED_ORIGINS=https://<vercel-client-host>
AUTH_REFRESH_COOKIE_SAMESITE=None
```

Vercel and Render are cross-site, so the refresh cookie must use
`SameSite=None` with secure cookies enabled.

Secure cookies remain enabled by default. Do not set
`AUTH_REFRESH_COOKIE_SECURE=0` in production.

## Neon Postgres

Create a Neon project and use the pooled PostgreSQL connection string for
`DATABASE_URL`. Use the pooled string for Render because the world/auth process
uses short-lived query bursts for login, character selection, and save snapshot
flushes.

Do not add fake `SELECT 1` keepalive jobs to keep Neon awake. The database is
only for account/session data, character records, and `character_saves`
snapshots. During play, the world server keeps the authoritative state in
memory; important save changes are marked dirty and flushed by autosave or
final session cleanup.

The server creates the database tables on startup when `DATABASE_URL` is
present. For an explicit managed DB readiness check, run:

```bash
DATABASE_URL=<Neon pooled connection string> npm run db:check
```

`db:check` creates the schema if needed and prints row counts for the auth and
character tables. This is a manual readiness check, not a production keepalive.

## Render Server

Use `render.yaml` as the source of truth for the Render Web Service. It defines:

- `darksaber-world-server`: Node Web Service
- `AUTH_JWT_SECRET`: generated by Render
- `AUTH_ALLOWED_ORIGINS`: entered in the Render Dashboard

Render Blueprint deployment:

1. Push the repository to GitHub.
2. In Render, create a Blueprint from this repository.
3. During Blueprint setup, fill `AUTH_ALLOWED_ORIGINS` with the final Vercel
   client origin, for example `https://darksaber.example.com`.
4. Deploy the Blueprint.
5. Confirm the server health endpoint:

```text
https://<render-service-host>/healthz
```

The JSON must include:

```json
{ "authStore": "postgres" }
```

Set these Render environment variables:

```text
DATABASE_URL=<Neon pooled connection string>
NODE_ENV=production
AUTH_JWT_SECRET=<long random>
AUTH_ALLOWED_ORIGINS=https://<vercel-client-host>
```

Render Free Web Services may sleep when there is no traffic. While a player has
the world WebSocket open, the client sends `CLIENT_HEARTBEAT` about every 45
seconds and the server responds with `SERVER_HEARTBEAT_ACK`. This traffic is not
written to the database and is accepted before or after `WORLD_JOIN`. WebSocket
close/reconnect clears and recreates the client timer so duplicate heartbeats do
not accumulate.

## Vercel Client

Import this repository in Vercel and set:

```text
VITE_AUTH_SERVER_URL=https://<render-service-host>
VITE_WORLD_SERVER_URL=wss://<render-service-host>
```

Use the default Vite deployment. `vercel.json` pins:

- Build command: `npm run build`
- Output directory: `dist`

After deployment, copy the Vercel production origin back into Render's
`AUTH_ALLOWED_ORIGINS`. If you use a custom domain, use the custom domain origin.

## Required Production Checks

Before opening access to players:

1. `/healthz` returns `authStore: "postgres"`.
2. Vercel client loads with production `VITE_AUTH_SERVER_URL` and
   `VITE_WORLD_SERVER_URL`.
3. Register a new account.
4. Log out and log back in.
5. Create a character.
6. Refresh the browser and confirm `/auth/refresh` restores the session.
7. Enter the world and confirm WebSocket `WORLD_JOIN` succeeds.
8. Restart the Render server and confirm the account/character still loads from
   PostgreSQL.

## Data Operations

Account data lives in managed PostgreSQL. Production operation must include:

- scheduled database backups
- manual restore rehearsal before broad release
- environment-specific `AUTH_JWT_SECRET` rotation plan
- periodic review of Render service logs for auth and WebSocket errors

Do not use local-only databases as a production substitute. Do not publish a
build that points users at a local machine or temporary database. Do not add
Docker/local Postgres as a production path.
